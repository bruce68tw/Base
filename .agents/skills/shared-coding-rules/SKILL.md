# 共用開發規則

先遵守工作專案與目標檔案範圍的 AGENTS.md，保留既有修改。此處集中維護使用者確認的開發慣例，不複製各模組的 API 文件，也不將單次實作選擇當成通用要求。

## 依修改範圍讀取

- 前端 TypeScript、瀏覽器請求與 UI：讀 [前端規則](references/frontend.md)。
- 後端 C#、Controller 與共用服務：讀 [後端規則](references/backend.md)。
- 同時修改前後端時讀兩份；只修改一側時無須載入另一側。
- 使用共用 API 時，另按實際相依讀取該模組自己的 skill、模型與來源；本 skill 不取代模組契約。

## 命名規則（使用者已確認）

前後端變數均使用 lowerCamelCase，名稱簡單清楚，可用複合字，原則上採動詞加名詞。此規則只涵蓋變數，不擴大至未討論的欄位、屬性或常數。函數命名依前後端 references 的規則。

### MVC 資料表功能對應

以下僅適用 MVC 功能，不推廣至 Flutter 或 RPA。以資料表名稱作功能前綴；以 `Order` 為完整對應例子：

| 檔案路徑 | 類別或用途 |
| --- | --- |
| `Controllers/OrderController.cs` | 類別 `OrderController`，保留 `Controller` 後綴 |
| `Services/OrderRead.cs` | 類別 `OrderRead`，負責 CRUD 查詢 |
| `Services/OrderEdit.cs` | 類別 `OrderEdit`，負責編輯 |
| `Services/OrderSvc.cs` | 類別 `OrderSvc`，負責該資料表存取 |
| `Views/Order/Read.cshtml` | 查詢畫面 |
| `Views/Order/Edit.cshtml` | 編輯畫面 |
| `_src/tsView/Order.ts` | 對應功能的前端 TypeScript 原始檔 |

後端服務檔名與類別名一致，使用大駝峰（PascalCase），後綴確切為 `Read`、`Edit`、`Svc`，不寫成全大寫。`Views` 子目錄與功能 TypeScript 檔名不含 `Controller`；其他畫面依系統需要命名。

## 設計、可讀性與函數拆分（使用者已確認）

以目前需求為準，優先採用簡單直接的設計，不為尚未確定的需求預先增加抽象層或擴充機制；目前需求所需的抽象仍可採用。

以容易閱讀為優先，避免巢狀三元運算，以及把過多處理塞進同一行。

一個函數聚焦一項工作；重複或複雜步驟抽成小函數，不硬訂行數。

註解主要說明商業規則、特殊限制與採用某種寫法的原因，避免重述程式碼已清楚表達的動作。程式較多時，在每個邏輯區塊加上註解，簡要說明用途。

註解與開發文件預設使用繁體中文，程式識別名稱及必要技術名詞保留原文。

## 優先重用既有共用程式

此原則同時適用前端與後端。共用模組已整理、精簡並經使用者驗證，實作前先查既有封裝，避免重寫相同邏輯。

- 先依工作需求讀取相關模組的使用 skill；再以需求關鍵字、既有呼叫範例搜尋實際來源，核對函式參數、回傳值、錯誤與非同步契約，不憑名稱猜 API。
- 已有符合需求的共用函式時優先呼叫。只有查證現有封裝確實不適合時，才新增或自行實作，並說明缺口；不為套用封裝而擅自改動其公開契約。
- 模組使用 skill 以「需求 → 類別／函式 → 來源與範例」建立查找入口，詳細用法留在模組內維護，不在此複製函式清單。前端封裝到應用的實際 TypeScript 共用來源查證，不假設 C# 模組 skill 涵蓋瀏覽器 API。
- 完成回報簡述本次重用的關鍵共用類別／函式；若相關需求改採自行實作，交代現有封裝不適用的原因。依變更範圍驗證，不把既有封裝曾測試過當成本次整合已驗證。

模組查找入口（依實際相依選讀）：[Base](../../../Base/.agents/skills/00-overview/SKILL.md)、[BaseApi](../../../BaseApi/.agents/skills/00-overview/SKILL.md)、[BaseAI](../../../BaseAI/.agents/skills/00-overview/SKILL.md)、[BaseWeb](../../../BaseWeb/.agents/skills/00-overview/SKILL.md)。移動 checkout 後以專案實際參照重新定位。

## 暫緩整理事項

多國語處理暫緩整理，本次不訂新規則；不代表停用既有多國語功能。

## 累積與維護

新增規則時記錄適用範圍、原則、具體範例與已知例外。只納入使用者已確認的規則；從舊程式推測的寫法先標為待確認，不直接升為通用規範。

規則與既有公開契約不一致時，說明差異並依本次授權範圍處理，不順手全面重構。引用實際來源時仍需重新核對；規則文件不代表既有程式已全部符合。

程式變更依工作專案既有方法檢查；分開回報編譯、離線驗證與外部服務驗證。
